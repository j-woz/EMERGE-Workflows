=== The partial output question

____
what is your plan here
____

Asked in response to a comment claiming the partial file was deleted
when nothing deleted it.  `System.exit()` inside try-with-resources
skips the writer's `close()` , leaving a footerless, unreadable stub
that would also block the next run via the new exists-check.  Two
options were put forward: delete the partial file, or keep it and fix
the comment.

____
do 2.  add a note to the footer that the file is incomplete
____

This required the abort to unwind rather than call `System.exit` , so
the writer closes and the footer is written.  `MetadataParquetWriter`
gained a `finalizeWrite()` override so metadata added *during* writing
still reaches the footer.  A duplicate now leaves valid Parquet carrying
an `incomplete` key that states the reason.

____
do that but put the contents of the exception handler in a function
____

== Phase 6: Performance investigation

_2026-09-17 / 2026-09-19 15:04_

____
when done, try some of your smaller files with and without -c and
report on the timing differences
____

7 of 17 columns: 3.0 s vs 3.3 s, output 1.52 MB vs 4.37 MB.  About 19%
faster, 2.9x smaller.

____
how do you handle the infected and deaths lists in the JSON right now
____

They are dropped.  The converter reads only `task_id` , `params_id` ,
`seed` , and `output_dat` ; everything else is parsed and discarded
without warning.  Both lists hold `day_final + 1` ints, one per day,
matching the per-Day row count -- so they would map onto existing rows
as two more columns.  Not implemented.

____
is 30 MB/s a typical read rate for JSON
____

No -- on the low side.  Only ~45% of each 64 KB block is real JSON, the
rest NUL padding, so 30 MB/s of file is ~13 MB/s of parsed JSON.
json-simple typically runs 30-80 MB/s; Jackson streaming 200-500 MB/s.

____
can we increase the size of the java read buffer
____

Measured rather than assumed.  `strace -c` showed 5,334 read syscalls
totaling 0.078 s of a 4.6 s run -- *1.7% of runtime*.  `/usr/bin/time
-v` showed 7.98 s user CPU against 3.85 s wall.  The conversion is
CPU-bound, not I/O-bound, so a larger buffer would optimize 1.7% of the
work.  Recommended against.

____
do the padding fix
____

Trim NUL padding before the UTF-8 decode, at all four decode sites.
Benchmarked with 5 alternating runs of before/after jars: 3.30 s ->
3.18 s mean, a *3.6% gain* -- less than predicted, because ASCII
`String` decoding is already near `memcpy` speed and the char-by-char
re-escaping loop never touched the padding anyway.  Output verified
byte-identical.  Kept: it is five lines, strictly less work, and avoids
~64 GB of pointless UTF-16 allocation across a full 12 GB run.

The remaining lever is parallelism -- records are independent, and the
parse is single-threaded while cores sit idle.

____
keep the padding fix and let me commit that
____

== Open items

* `infected` and `deaths` remain undocumented and unconverted
* Parallel parsing across blocks is unimplemented; it is the one change
  likely to give a large speedup.  Note that duplicate reporting is
  currently "first in file order", which parallel parsing would make
  nondeterministic unless duplicates are collected and reported after
  the join
* `result.parquet.bad` (139 MB, footerless) and `tmp/` (~125 MB of
  fixtures) remain in `out-1B-1-11` pending cleanup
