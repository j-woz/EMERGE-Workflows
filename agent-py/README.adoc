= Agent Workflow via Python Invocation (agent-py)

The idea here is to support running 1M or more ExaEpi runs in a single workflow.

This directory contains a workflow and Python features for running the ExaEpi `agent`.

== Support

Please file issues on this repo with any problems, questions, or documentation clarification ideas.

== Overview

The Swift/T workflow and Python modules in this directory:

* Generate and modify ExaEpi configuration files in local storage
* Execute ExaEpi agent runs with custom parameters in local storage
* Efficiently log to and retrieve results from agent executions in the shared filesystem.
** All result parameters are appended into a single log, formatted as JSON strings.
** A single Swift/T worker funnels all output values into this log.
** This avoids the many-small-file problem.

== Quick start

----
$ swift-t -n $PROCS loop-local.swift template.cfg $N $POP $CASES results.log
----

----
$ swift-t -n $PROCS loop-local-replicates.swift template.cfg $PARAMS_CSV $N $POP $CASES results.log
----

where:

* `PROCS`: the process count
* `template.cfg`: the template cfg file which will be edited for each `agent` run
* `PARAMS_CSV`: The CSV file of pre-generated parameters
* `POP`: the population data file
* `CASES`: the cases data file
* `results.log`: the output JSON log file

The `loop-local.swift` calls into the Python libraries below to run the ExaEpi `agent` and perform I/O.

The format of `results.log` is a list of 4096-byte blocks, each of which contains a NUL-padded JSON string that contains the result data, e.g.:

=== Rank counts

`loop-local-replicates.swift` requires 3 workers, 1 for the CSV input stream, 1 for the JSON log output stream, and 1 for general work.  The I/O stream workers can also do normal work (ExaEpi) when not busy with I/O.

== Workflows

=== `loop-local.swift`

The main workflow entry point is `loop-local.swift`, which orchestrates multiple agent runs, each with a different random `seed`:

[source,c]
----
import agent;  // imports the ExaEpi agent API

// Command-line arguments:
// 1: template_cfg - path to ExaEpi configuration template
// 2: total - number of runs to execute
// 3: urbanpop - urbanpop data file basename
// 4: cases - cases data file
// 5: result_file - output file for results

foreach idx in [0:total-1]
{
  int seed = randint(0, 10*1000*1000);
  result = agent(idx, template_cfg, seed, urbanpop, cases, p);
  result_log(result_file, result);
}
----

The workflow:

. Iterates over `total` run indices
. Generates a random seed for each iteration
  . Calls `agent()` (mapped to Python's `exaepi_agent.run()`) with:
  ** Run index
  ** Template configuration file
  ** Random seed
  ** Data file references
  ** Parameter dictionary for anything additional (currently empty)
. Logs each result via `result_log()` to a binary result file
. Results are stored in 1024-byte blocks indexed by run number

The `result_log()` function in the Swift workflow calls the Python `result_log.do_write()` to persist results to disk using the dedicated last worker process (rank _n-1_, accessed via the Swift/T `@location` syntax).

=== `loop-local-replicates.swift`

As `loop-local.swift` but supports replicates

IDs:

* `task_id`:   A unique ID generated for each task by the workflow layer
* `cfg_id`:    An ID in the `input.cfg` file, key `id`.  If this is defined in a reused `template.cfg`, this is not unique.
* `params_id`: The ID of the row in the input `PARAMS_CSV` file

So each ExaEpi run has 3 unique IDs, which are not the same, because they come from different sources!

=== Data broadcast

See `hook.tcl` for the list of files broadcast to the local storage.

* The `template_cfg` comes from the script command line which turns into an environment variable
* Everything else, including programs, comes from `../data-sets`

== Python layer: `exaepi_agent.py`

. Configure a template ExaEpi input file
. Call `exaepi_agent.run()` with parameters:
   * Random seed and other sweep parameters
   * Path to template configuration
   * References to data files
. Configuration is generated via `cfg_edit.py`
. ExaEpi agent executes via `mpiexec`
. Results are collected and returned

== Underlying Python modules

=== exaepi_agent.py

Main interface for running ExaEpi agent instances.

* `run(idx, template_cfg, seed, urbanpop, cases, params)` - Execute a single agent run
** `idx` - integer index for the run
** `template_cfg` - path to the original configuration file
** `seed` - random seed value
** `urbanpop` - basename of urbanpop file (assumed in workdir)
** `cases` - cases file reference
** `params` - dictionary of additional parameters to modify
** Returns: string representation of result dictionary with `idx` and `seed`

* Supporting:
** `run_exaepi()` - Spawns the ExaEpi agent using `mpiexec`
** `get_results()` - Parses results from agent output

=== cfg_edit.py

Utility for generating ExaEpi configuration files from templates.
Used as a library from the workflow.

* `process()` - Generate a modified configuration file with custom parameters
* Modifies template configuration with provided parameter values
* Handles JSON-based configuration editing
* Supports key=value parameter format
* Supports command-line use for debugging:

Usage:
[source,bash]
----
python cfg_edit.py <template_cfg> <input_cfg> <rundir> [options]
  -s, --seed       int seed (default: 0)
  -p, --param      parameter to modify as KEY=VALUE (repeatable)
  -v, --verbose    enable verbose output
----

=== result_log.py

Manages result logging for agent executions by stuffing Python strings into 4096-byte NUL-padded blocks.
Used as a library from the workflow.

==== Library routines

* `do_open_write()` - Open log file in write mode
* `do_open_read()` - Open log file in read mode
* `do_write()` - Write a result record (encoded as UTF-8 to 4096-byte block)
* `extract()` - Retrieve result from specific block index

==== Command line usage

Also provides a command-line interface for interactive extraction.

Usage:
[source,bash]
----
$ python result_log.py extract <filename> [idx ...]
----

You can also extract this data with `dd bs=4K skip=N count=M ...` and `tr`.

For example, to extract the 12th block from the file, do:

[source,bash]
----
$ python result_log.py extract result.log 12
----

or

[source,bash]
----
$ dd bs=4K skip=12 count=1 if=results.log | tr -d '\0'
----

==== Data format

We preprocessed the input parameter files with `insert-params-id.sh`, which prepends a unique `param_id` integer to each row.  This corresponds to the matching output record.

Each JSON record contains:

* "day_final": The last day number in the run.  Early stopping is possible if the infected count hits 0
* "idx": A unique number generated by the workflow for each ExaEpi run
* "params_id": The record number in the input CSV
* "seed": The random seed generated by the workflow
* "infected": The infected count scraped from the ExaEpi output
* "deaths": The death count scraped from the ExaEpi output
* "start": The start time in seconds since the Unix Epoch
* "stop": The stop time in seconds since the Unix Epoch

== Parquet generation

We convert the result log into a Parquet file with `./log2pqt` .
We used a Java program for this because we may need to parallelize.

NOTE: Our JSON is slightly malformed with literal NLs in the `output_dat` entry.  Our JSON-parsing Java and Python (`validate_pqt.py`) handle this with preprocessing.

. Build the tool with `./build-log2pqt.sh`
. Run with `./log2pqt`
. Preview  the Parquet with `./show_pqt`
. Validate the Parquet with `./validate_pqt`
